# Dorks Tavily : plan de mise en œuvre

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** une étape « dorks » à la fin de l'enquête : Tavily envoie une liste fermée de requêtes à deux informations (nom et valeur confirmée, pseudo et plateforme, nom et mot-clé), et le moteur classe les pages selon le genre du dork.

**Architecture:** la liste des dorks et le filtre des deux informations sont des fonctions pures dans le dossier `tavily`. Tavily gagne une méthode facultative `dork` sur le port `Source`. Le moteur l'appelle une fois la file vide, avec le contexte des valeurs confirmées et le reste du plafond.

**Tech Stack:** TypeScript strict, zod 4, Vitest, Next.js 16.

**Spec:** `docs/superpowers/specs/2026-11-27-dorks-design.md` (et T5, T6, T9, T11 dans `docs/DECISIONS.md`).

## Écarts à la spec (choix de l'assistant)

- La console `/dev` ne montre pas les réponses brutes des dorks (panneau « sources ») : le panneau « Enquête complète » montre déjà les pages gardées. Moins de code ; à ajouter si le test réel des opérateurs le demande.
- Au deuxième tour, seules les valeurs confirmées pendant ce tour servent (par exemple par un compte confirmé). Une carte search.ch choisie reste un affichage : la route ne transmet pas les valeurs confirmées. Le code le note par un commentaire `shortcut:`.
- Un compte F2 trouvé par un dork et coché par le visiteur est cherché au deuxième tour comme les autres comptes (comportement existant de `accountAddresses`).

## Review Focus

- Un guillemet dans un nom ou une valeur (`Léa "Lily" Martin`) ne casse pas la requête : les `"` sont retirés des valeurs. Tâche 1.
- Un titre au nom inversé (« Martin Léa - Résultats ») est gardé ; « Léa Martinez » est jeté. Tâche 1.
- Sans `NOM` saisi, seul le dork pseudo part ; sans pseudo ni nom, aucun appel. Tâches 1 et 3.
- Un quota atteint au milieu des dorks garde les pages déjà trouvées et signale l'échec. Tâches 2 et 3.
- La même adresse trouvée par deux dorks donne un seul constat. Tâche 3.

### Task 1: Liste des dorks et filtre des deux informations

**Files:**

- Modify: `src/server/domain/source.ts` (types du contexte)
- Create: `src/server/providers/tavily/dorks.ts`, `src/server/providers/tavily/dorks.test.ts`

**Interfaces:**

- Produces (dans `source.ts`) :
  - `type DorkKind = "value" | "pseudo" | "keyword"`
  - `interface DorkContext { name?: string; values: Partial<Record<"C1" | "E1" | "D1" | "ORGA", string[]>>; pseudo?: { value: string; rare: boolean }; onlyValues: boolean }`
- Produces (dans `dorks.ts`) :
  - `interface Dork { kind: DorkKind; field: FieldCode; query: string; second: string[]; includeDomains?: string[]; site?: string[]; romandie: boolean }` : `second` liste les mots dont au moins un doit être dans le titre ou l'extrait ; `site` liste les domaines dont l'adresse doit faire partie (dork 4).
  - `ROMANDIE = "(Neuchâtel OR Vaud OR Genève OR Fribourg OR Valais OR Jura)"`
  - `PRESS_DOMAINS: string[]` (liste de presse de `SOURCES.md` section 4)
  - `buildDorks(context: DorkContext): Dork[]` : les dorks applicables, dans l'ordre 1 à 8 de la spec.
  - `keepsPage(dork: Dork, name: string | undefined, page: { url: string; title: string; content?: string | null }): boolean`

- [ ] **Step 1: Write the failing tests** (`dorks.test.ts`), un `it` par dork, avec ces assertions :

```ts
const ctx = { name: "Léa Martin", values: { C1: ["Neuchâtel"], E1: ["Exemple SA", "Développeuse, Exemple SA"] }, pseudo: { value: "lmartin_06", rare: true }, onlyValues: false };
// dork 1
expect(buildDorks(ctx)[0]).toMatchObject({ kind: "value", field: "I1", query: '"Léa Martin" "Neuchâtel"', second: ["Neuchâtel"], romandie: false });
// dork 2 : la valeur la plus courte
expect(buildDorks(ctx)[1]).toMatchObject({ kind: "value", field: "E1", query: '"Léa Martin" "Exemple SA"', romandie: false });
// dork 4
expect(buildDorks(ctx).find((d) => d.kind === "pseudo")).toMatchObject({ field: "F2", query: '"lmartin_06" site:instagram.com OR site:tiktok.com OR site:facebook.com', site: ["instagram.com", "tiktok.com", "facebook.com"], romandie: true });
// dorks 5 à 8, dans cet ordre
expect(buildDorks(ctx).filter((d) => d.kind === "keyword").map((d) => [d.field, d.query])).toEqual([
  ["F2", '"Léa Martin" site:linkedin.com/in'],
  ["G1", '"Léa Martin" club OR résultats OR classement'],
  ["G3", '"Léa Martin"'],
  ["I3", '"Léa Martin" filetype:pdf'],
]);
// G3 porte includeDomains = PRESS_DOMAINS ; LinkedIn porte site ["linkedin.com"]
```

Autres tests : sans `name`, seul le dork pseudo ; sans `name` ni `pseudo`, `[]` ; `onlyValues: true` ne donne que les dorks `value` ; `ORGA` donne le dork 3 (champ D1) ; les `"` sont retirés d'un nom et d'une valeur. `keepsPage` : vrai pour le titre « Martin Léa - Neuchâtel » (dork 1) ; faux pour « Léa Martinez - Neuchâtel » ; faux si la ville manque ; dork pseudo : vrai pour `https://www.instagram.com/lmartin_06/` avec le pseudo dans le titre, faux pour une adresse hors des trois domaines ; dork G3 : vrai si l'adresse est sur un domaine de `PRESS_DOMAINS` et le nom dans le titre ; dork pseudo sans nom : le nom n'est pas exigé.

- [ ] **Step 2: Run** `npx vitest run src/server/providers/tavily/dorks.test.ts`. Expected : FAIL (module absent).
- [ ] **Step 3: Implement** `buildDorks` et `keepsPage` dans `dorks.ts`. Le nom est comparé avec `nameMatches` (`@/server/domain/name-match`) ; les mots de `second` et le pseudo sans tenir compte de la casse ni des accents. Une adresse est « sur un domaine » si son hôte est ce domaine ou finit par `.` + ce domaine.

### Task 2: Méthode `dork` de Tavily

**Files:**

- Modify: `src/server/domain/source.ts`, `src/server/providers/tavily/client.ts`, `index.ts`, `provider.test.ts`
- Create: `src/tests/fixtures/tavily/dork-found.json` (pages inventées, certaines qui passent le filtre, d'autres non)

**Interfaces:**

- Consumes : `buildDorks`, `keepsPage`, `ROMANDIE` (tâche 1).
- Produces :
  - `SourceRecord.dork?: DorkKind`
  - `Source.dork?(context: DorkContext, maxCalls: number, signal: AbortSignal): Promise<DorkResult>`
  - `interface DorkResult { calls: number; records: SourceRecord[]; failed?: "quota" | "error" }`
  - `search(query, apiKey, signal, options?: { country?: string; includeDomains?: string[] })` dans `client.ts`.
  - `MAX_SEARCHES` passe de 3 à 6 (T11 : 6 au premier tour, 2 au deuxième).
  - Commentaire de `SourceField.page` : I1, ou le champ rempli par un dork (F2, G1, G3, I3, E1, D1).

- [ ] **Step 1: Write the failing tests** (`provider.test.ts`) :

  - avec `maxCalls: 3` et un contexte qui donne 5 dorks, exactement 3 appels, les dorks 1 à 3 de la liste ;
  - relance : un dork `romandie` sans page gardée est relancé une fois sans `ROMANDIE`, après les premiers envois de tous les dorks et seulement s'il reste du plafond ; un dork `value` n'est jamais relancé ;
  - chaque page gardée devient `{ about: "subject", dork, fields: [{ field, value: url, page: { title } }], identifiers: [] }` ; `content` n'apparaît nulle part dans le résultat ;
  - réponse 432 au deuxième appel : `{ calls: 2, records: <pages du premier>, failed: "quota" }` ; réponse 500 : `failed: "error"` ;
  - `maxCallsPerInvestigation` vaut 6.
- [ ] **Step 2: Run** `npx vitest run src/server/providers/tavily`. Expected : FAIL.
- [ ] **Step 3: Implement** `dork` dans `index.ts` : premiers envois dans l'ordre, puis relances dans l'ordre, arrêt à `maxCalls` ou au premier échec. Réutiliser `tavilyResponseSchema` ; une réponse invalide compte comme `failed: "error"`. `SourceQuotaError` donne `"quota"`.

### Task 3: Étape « dorks » dans le moteur

**Files:**

- Modify: `src/server/investigation.ts`, `src/server/investigation.test.ts`, `src/server/domain/confidence.ts` (constantes)

**Interfaces:**

- Consumes : `Source.dork`, `DorkResult`, `SourceRecord.dork` (tâche 2).
- Produces : `MAX_PAGE_CARDS = 3`, `ROUND_TWO_DORK_CALLS = 2` (dans `confidence.ts`).

- [ ] **Step 1: Write the failing tests** (`investigation.test.ts`, source factice avec `dork: vi.fn()`) :
  - `dork` est appelé une fois, après tous les `investigate`, avec `maxCalls` = 6 moins les appels `investigate` déjà faits à cette source (plafond `maxCallsPerInvestigation: 6`) ;
  - le contexte contient `name` (le `NOM` saisi), `values.C1` venu d'un constat « confirmé » (source factice EMAIL qui renvoie C1 relié à l'email) et pas d'un constat « probable » ; `pseudo.rare` faux quand le pseudo est courant (même calcul que pour WhatsMyName) ;
  - deuxième tour (`alreadySearched` non vide) : `onlyValues: true` et `maxCalls` au plus 2 ;
  - `dork: "value"` donne un constat « probable », sans appel à `assessConfidence` (même avec un record sans indice) ;
  - `dork: "pseudo"` : « probable » si `rare`, sinon carte « à confirmer » ;
  - `dork: "keyword"` : les 3 premières pages sont des cartes « à confirmer » qui gardent leur champ (G1, G3, I3, pas seulement F2) avec `page.title` ; la 4e est comptée dans `hidden.possible` ;
  - la même adresse renvoyée par deux records donne un seul constat ;
  - `failed: "quota"` : les pages renvoyées sont traitées, puis un événement `source-failed` (`reason: "quota"`) ; `done` vient en dernier ;
  - aucun appel à `dork` sans `NOM` ni `PSEUDO` saisi ; une page de dork ne crée aucun `lead`.
- [ ] **Step 2: Run** `npx vitest run src/server/investigation.test.ts`. Expected : FAIL.
- [ ] **Step 3: Implement** : garder, au fil de l'enquête, les valeurs C1, E1, D1 des constats « confirmés » sur le visiteur et les `ORGA` confirmés, et le caractère courant du pseudo saisi. Après la boucle de la file et avant `done`, appeler `dork` des sources qui l'ont (sauf quota atteint), ajouter `calls` au compteur, traiter les records dans `handleRecord` : si `record.dork` est présent, le niveau vient du genre (tableau de la spec) au lieu de `assessConfidence`, et le filtre « F2 seulement » des cartes ne s'applique pas. Commentaire `shortcut:` sur le deuxième tour (valeurs d'une carte search.ch choisie non transmises, à faire si le panel montre le besoin).
